# AGENT.md - Developer Guide for storefront-saas-go

## Architecture Overview

This project follows Clean Architecture with strict separation of concerns:

```
Request -> Handler -> Service -> Repository -> Database
```

Each layer has a single responsibility and depends only on the layer below it through interfaces.

## Folder Responsibilities

| Package | Responsibility |
|---|---|
| `cmd/api/` | Entry point: wire dependencies, start HTTP server |
| `cmd/seed/` | Demo data seed command |
| `internal/config/` | Load environment variables into typed structs |
| `internal/db/` | Initialize GORM (SQLite/Postgres) and Redis |
| `internal/domain/` | Pure Go structs (no methods, no logic) |
| `internal/handler/` | Parse HTTP request, call service, return JSON |
| `internal/middleware/` | Cross-cutting concerns (CORS, auth, logging) |
| `internal/repository/` | GORM queries only. No business logic. |
| `internal/service/` | Business rules, validation, caching logic |
| `internal/util/` | Shared helpers (response formatting) |
| `docs/` | Generated by swaggo/swag. Do not edit manually. |
| `web/` | React 19 frontend (Vite + TypeScript + shadcn/ui) |
| `web/src/api/` | Generated by Orval. Do not edit manually. |
| `web/src/types/api.ts` | Generated by openapi-typescript. Do not edit manually. |

## Naming Rules

- Use intention-revealing names: `ListActiveStores`, `FindProductByID`, `CreateOrderWithValidation`
- Never use generic names: not `Update`, `Delete`, `Get`
- Repository methods describe the query: `ListActiveStores`, `FindStoreBySlug`, `DeactivateStore`
- Service methods describe the business action: `GetStoreBySlug`, `ListHotProducts`
- No emojis. No em-dashes. Plain English only.

## Adding a New Endpoint

Follow this exact process to maintain the codegen pipeline:

### 1. Add domain model (if new entity)

Edit `internal/domain/models.go`. Add the struct with JSON and GORM tags.

### 2. Add repository

Create `internal/repository/{entity}_repository.go`:
- Define an interface with intention-revealing method names
- Implement it using GORM

### 3. Add service

Create `internal/service/{entity}_service.go`:
- Define an interface
- Inject the repository interface (for testability)
- Add business logic and validation

### 4. Add handler

Create `internal/handler/{entity}_handler.go`:
- Inject the service interface
- Parse request, call service, return JSON with `util.RespondWithSuccess` or `util.RespondWithError`
- Add Swagger annotations on every handler function

### 5. Register routes

Edit `cmd/api/main.go` to wire the repository, service, and handler, then add the route.

### 6. Run codegen

```bash
make codegen
```

This runs:
1. `swag init` - parses Go annotations -> `docs/swagger.json`
2. `swagger2openapi` - converts to OpenAPI 3 -> `docs/openapi.json`
3. `openapi-typescript` - generates TypeScript types -> `web/src/types/api.ts`
4. `orval` - generates TanStack Query hooks -> `web/src/api/`

### 7. Use generated hooks in frontend

The generated hooks in `web/src/api/` are ready to use with `@tanstack/react-query`.

## Database Switch

### Local development (SQLite, default)

```env
DB_DRIVER=sqlite
DB_DSN=file:./dev.db
```

No setup required. SQLite file is created automatically.

### PostgreSQL (for production or Docker)

```env
DB_DRIVER=postgres
DB_DSN=host=localhost user=storefront password=storefront dbname=storefront port=5432 sslmode=disable
```

GORM auto-migrates all models on startup. Switching drivers only requires updating these two env vars.

## Redis Caching

The product service caches `ListHotProducts` results in Redis with a 5-minute TTL. If `REDIS_URL` is empty or Redis is unavailable, the service falls back to direct database queries.

Cache key: `hot_products:{page}:{limit}`

To add caching to a new service method:
1. Inject `*redis.Client` into the service struct
2. Check the cache before querying the database
3. Set the cache after a successful database query
4. Use `json.Marshal`/`json.Unmarshal` for serialization

## Clean Code Checklist

Before opening a pull request:

- [ ] Handler only parses request and calls service (no business logic)
- [ ] Service method name is intention-revealing (not generic)
- [ ] Repository only contains GORM queries (no business logic)
- [ ] All service dependencies are injected via interfaces
- [ ] Every HTTP handler has Swagger annotations
- [ ] `make codegen` was run after any handler changes
- [ ] `make test` passes
- [ ] No emojis, no em-dashes in code or comments

## Removing Demo Data

All demo/seed data is in `cmd/seed/main.go`. To remove it:

1. Delete the file: `rm cmd/seed/main.go`
2. Remove the `make seed` target from `Makefile`
3. Do not run `make seed` in production

The demo stores ("Demo Store One", "Sample Marketplace") and their products are only created by running `make seed` and never auto-seeded on startup.

|---|---|---|
| `PORT` | `8080` | HTTP server port |

| `DB_DRIVER` | `sqlite` | Database driver (sqlite or postgres) |
| `DB_DSN` | `file:./dev.db` | Database connection string |
| `REDIS_URL` | `` | Redis connection URL (optional) |
| `JWT_SECRET` | `` | JWT signing secret |
| `CORS_ALLOWED_ORIGINS` | `*` | Comma-separated allowed origins |
